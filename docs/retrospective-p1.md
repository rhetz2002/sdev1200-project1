During the beginning I tried to logic out how the loop would be best laid out and figure out which parts would best be fit to be in secondary files. I then did a rough outline of the game and built the rest of it off that framework. During testing I tried to look at the game through the lens of how a player would interact with it rather than how inputs could affect the code. I then took that information and corrected what I found during testing. Lastly before the final release I tried to clean up some things I personally didn't like with the code namely how I imported sprites. I then published the final release with v.2.1.2                

I think the main thing that didn't go according to plan would be how I planned the enemies to move and spawn. I would of originally liked them to spawn more at random but for ease of programming I didn't go that route. I also would have liked them to move more as a cluster, but I also didn't do that for the same reason. Lastly the main file feels a bit bloated and I think that is due to a weakness in my planning process which if I could do this over again, I would plan a bit more carefully and put a bit more effort into my sudo code.                        
                    
In terms of lessons I'm going to be taking forward into the next project, two stick out the most. The main one is going to be trying to plan more carefully as I feel like that was the main reason for the bloated main file as currently, I have ideas of what can be moved but I think moving entire things in this stage increases the possibility of errors to the point that it may not be worth it especially this close to the deadline. Lastly I think I'm going to be taking the lesson I learned about bug testing and how I approach it in terms of how the user would interact with the software.
