I didn't learn much about the code from testing aside that lts surprisingly stable all things considered it didn't crash even once while testing. That and I forgot to implement the despawn for the players' bullets which caused major lag, but I feel I learned a decent bit more about testing in general. The main thing that came to light was that a different approach to testing was required. When i was testing the Excell to SQL converter i looked for ways that the user input could cause errors but that was a verry limiting with this project as there was only five inputs W,A,S,D and space but it occurred to me that another way to approach testing was genuinely thinking of how a user may interact with the program rather than strictly how user inputs would interact with the code. This led to less direct errors found but still led to some issues being found. Not sure how valid this approach is, but I feel it's somewhat valid.
